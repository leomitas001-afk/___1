# Конструктор меню — data.json

Набор данных для приложения, которое собирает меню из основных блюд, гарниров и овощных добавок, проверяет ограничения и рассчитывает покупки. Включает принятые части 1–5 и дополнение 4б. Версия схемы: `1.0.0`, язык: русский.

Положите этот README рядом с `data.json`. Сам JSON содержит данные и пример меню; генератор меню, интерфейс и исполняемый валидатор в него не входят.

## Состав файла

| Раздел | Содержание | Количество |
| --- | --- | ---: |
| `meta` | Схема, перечисления, профиль, правила приготовления и пояснения | — |
| `ingredients` | Справочник ингредиентов | 118 |
| `mains_meat` | Основные мясные блюда, включая варианты с казылыком | 22 |
| `mains_special` | Рыба, рыбный фарш, печень и сердца | 17 |
| `sides` | Гарниры из круп и бобовых | 24 |
| `veg_addons` | Овощные добавки: 20 сырых и 8 паровых | 28 |
| `fruits` | Отдельные порции фруктов | 10 |
| `rules` | Ограничения для планировщика | — |
| `plan_sample` | Пример на 28 дней, по два приёма в день | 56 приёмов |
| `status` | Информационный текст о сборке | — |

Всего 101 карточка: 39 основных блюд, 24 гарнира, 28 овощных добавок и 10 фруктов. Новые сезонные добавки части 4б имеют ID `v_raw_13`–`v_raw_20`.

## Формат и связи

- Кодировка — UTF-8; синтаксис — JSON без комментариев и завершающих запятых.
- Числа записаны с десятичной точкой, без разделителей разрядов. Даты — `YYYY-MM-DD`.
- `id` — постоянный идентификатор. Название можно менять, сохраняя ID и ссылки на него.
- В карточках `ingredients[].id` ссылается на `ingredients[].id` справочника, а `g` задаёт массу.
- `main_id` плана ищется в объединении `mains_meat` и `mains_special`; `side_id` — в `sides`; `veg_id` — в `veg_addons`; `fruit_id` — в `fruits`.
- Допустимые значения перечислений находятся в `meta.enums`. Дополнительные правила интерпретации — в остальных полях `meta`.
- Значения `null`, `false` и `0` сохраняйте при импорте. Числовые флаги `0`/`1` в `rules` трактуются как выключено/включено.
- `status` предназначен для человека; он не заменяет проверку данных.

## Поля карточек

| Карточка | Основные поля |
| --- | --- |
| Ингредиент | `id`, `name`, `category`, `unit`, `storage`, `season`, `substitutes` |
| Основное блюдо | `protein`, `freq`, `method`, `program`, `temp_c`, `time_min`, `active_min`, `ingredients`, `steps`, КБЖУ |
| Гарнир | `grain`, `big`, `ingredients`, `cook`, `steps`, `active_min`, КБЖУ |
| Овощная добавка | `type`, `ingredients`, `prep`, `season`, КБЖУ; для `steam` — условия совместимости с гарниром |
| Фрукт | `ingredients`, `season`, КБЖУ |

`protein` — группа белкового продукта для проверки повторов, а не количество белка. Количество белка хранится в `p`. Группа `fish_cod` объединяет треску и минтай; конкретный продукт определяется ингредиентом. `grain` объединяет варианты одной крупы: например, разные виды риса всё равно считаются повтором риса.

`active_min` — активное время работы человека, `time_min` — основная тепловая обработка. Разогрев прибора может потребовать дополнительного времени. У гарнира режим и время находятся внутри `cook`. `temp_c: null` означает отсутствие заданной числовой температуры.

## Порции, массы и КБЖУ

Все карточки рассчитаны на одну порцию. `kcal` — килокалории, `p` — белки, `f` — жиры, `c` — углеводы в граммах **на всю порцию**, а не на 100 г.

Массы ингредиентов относятся к сырой съедобной части. Мясо и рыба — без костей, кожи, видимого жира и глазури, после размораживания; крупы — сухие; консервированные бобовые — после слива жидкости и промывания. Яйцо учитывается без скорлупы. Все количества в карточках записаны в `g`, включая воду. Технологическая вода для пара не входит в съедобную порцию.

Один приём пищи = основное блюдо + гарнир + овощная добавка. КБЖУ приёма — сумма трёх карточек. Фрукт назначается отдельно на день и не входит в целевые показатели отдельного приёма.

Цели конструктора: **700–850 ккал и 45–55 г белка на приём**. Если основное блюдо содержит менее 250 ккал, нужен гарнир с `big: true`; итоговую сумму всё равно проверяют. Масло дополнительно не добавляется. Сырые овощные добавки подаются без масла, заправок и соусов.

В файле `daily_target_confirmed: false`: индивидуальная суточная норма не подтверждена. КБЖУ карточек приблизительные. Справочник ингредиентов не содержит таблицы пищевой ценности на 100 г, поэтому для пересчёта изменённых рецептов нужны внешние данные или маркировка продуктов.

## Ограничения планировщика

Частотная категория берётся из `freq` основного блюда.

| Категория | Ограничение |
| --- | --- |
| `regular` | Без отдельного частотного интервала; общие ограничения действуют |
| `fish_weekly` | 1–2 события в любом полном скользящем окне из 7 дней |
| `liver_14d` | Не чаще одного события за 14 дней; обе разновидности печени имеют общий интервал |
| `hearts_30d` | Не чаще одного события за 30 дней |
| `fishmince_30d` | Не чаще одного события за 30 дней |
| `kazylyk_21d` | Не чаще одного события за 21 день; все блюда с казылыком имеют общий интервал |

В текущей схеме рыбный фарш имеет собственную категорию `fishmince_30d`; пример проверки `fish_weekly` считает события именно по `freq`, без добавления рыбного фарша. Если приложение должно учитывать всю рыбу суммарно, это правило нужно определить отдельно.

Один `protein` допускается максимум два календарных дня подряд: день считается использованным, если этот белок был хотя бы в одном приёме. Одинаковый `grain` запрещён в соседних приёмах, включая переход между днями. Повтор одного `main_id` допускается с разницей дат не менее 10 дней.

Для минимального интервала N разница календарных дат должна быть не меньше N. Скользящее окно N дней включает текущую дату и N−1 предыдущих дат. Проверки продолжаются через границы недель и планов; требуется история как минимум за 30 предыдущих дней. Пустая история не подтверждает соблюдение ограничений до начала плана.

## Овощи на пару и сезонность

При `has_steamer: false` планировщик выбирает только овощные добавки `type: "raw"`. При включении паровых добавок нужны поддержка прибора, подходящий `compatible_side_ids` и соблюдение условий совместной закладки. Овощи готовятся вместе с гарниром на его программе и времени.

Это переключатель **овощных добавок**: он не отключает автоматически основные блюда с программой `Пар`. Возможность приготовления таких основных блюд приложение должно проверять отдельно по доступному оборудованию.

`season` означает предпочтительный сезон покупки. Это не строгий запрет на использование в другие месяцы. `all` означает круглый год. У добавок `v_raw_13`–`v_raw_20` указаны `autumn`, `winter`, `spring`; свёкла и корневой сельдерей в них натираются сырыми.

## Хранение и покупки

Дни покупок по умолчанию — суббота и среда (`default_weekdays_iso: [6, 3]`, где понедельник — 1). Рыбу, печень, сердца, птицу и фарш планируют к приготовлению в день покупки или на следующий день. Для более позднего приготовления предусмотрена заморозка в день покупки с последующим размораживанием в холодильнике. Конкретные условия находятся в `rules.storage` и `meta.storage_policy`; более короткий срок маркировки имеет приоритет.

`ingredients[].storage` — базовое свойство продукта. `main_storage` в плане — фактический способ хранения сырья для конкретного основного блюда (`fresh` или `freezer`), а не срок хранения приготовленного блюда.

Расчёт покупки для выбранного периода:

1. Собрать ингредиенты основных блюд, гарниров, овощей и ежедневных фруктов.
2. Умножить количества на число порций и суммировать по ID ингредиента.
3. Исключить `water`, `salt`, `black_pepper`, `bay_leaf`.
4. Вычесть доступный запас, не допуская отрицательного количества.
5. Округлить покупку до упаковок, если известны их размеры.

Консервированные нут и фасоль покупаются в банках по 400 г нетто, но потребность в рецептах задана **без жидкости**. Число банок = округление вверх от потребности в граммах, делённой на массу продукта без жидкости в одной банке (`label_drained_weight_g_per_can`). Нельзя делить потребность на 400 г без проверки массы после слива. Эта характеристика должна поступать из маркировки: в справочнике она не заполнена отдельным полем.

Списки покупок задают массу съедобной части без поправки на очистку овощей и фруктов. Реальные остатки продуктов, размеры упаковок и потери при очистке приложение учитывает отдельно.

## Тестовый план

`plan_sample` охватывает **19.10.2026–15.11.2026**. Внутри `weeks[].days[]` находятся дата, номер дня, дата покупки запаса, `fruit_id` и два приёма в `meals`.

В приёме `weekday_only: true` соответствует понедельнику–пятнице, `false` — субботе–воскресенью. Это признак календарного дня в примере, а не ограничение доступности рецепта. Праздничные переносы не учитываются.

- `opening_inventory` — начальный запас с покупки 17.10.2026, покрывающий 19–20 октября.
- `week_1_shopping` — две покупки: 21 октября на дни 3–5 и 24 октября на дни 6–9, включая понедельник и вторник второй недели.
- `week_1_shopping_total` — сумма этих двух покупок; начальный запас в неё не включён.
- `purchase_calendar` — календарь покупок для плана; подробные списки приведены только для двух покупок первой недели.
- `prior_history` пуст, `history_is_synthetic: true`: пример не содержит реальной истории питания.

В сохранённом разделе `validation` указано: 56 из 56 приёмов соответствуют обоим диапазонам; калорийность — 700–807 ккал, белок — 45,8–55 г. Суммарно за 28 дней: 41 303 ккал без фруктов, 44 087 ккал с фруктами и 2 873,2 г белка без фруктов. Эти значения относятся к исходному примеру и после правок должны пересчитываться.

## Подключение к приложению

Минимальный пример чтения в Python, запускать из папки с `data.json`:

```python
import json
from pathlib import Path

data = json.loads(Path("data.json").read_text(encoding="utf-8"))
mains = {r["id"]: r for r in data["mains_meat"] + data["mains_special"]}
sides = {r["id"]: r for r in data["sides"]}
vegetables = {r["id"]: r for r in data["veg_addons"]}

meal = data["plan_sample"]["weeks"][0]["days"][0]["meals"][0]
cards = [mains[meal["main_id"]], sides[meal["side_id"]], vegetables[meal["veg_id"]]]
totals = {key: round(sum(card[key] for card in cards), 1)
          for key in ("kcal", "p", "f", "c")}
print(totals)
```

Для первого приёма результат: `kcal = 766`, `p = 52.1`. Это пример разрешения ссылок и сложения КБЖУ, не полный валидатор.

## Изменение и проверка данных

При добавлении карточек сохраняйте уникальность ID, структуру полей и ссылки на существующие ингредиенты. Не удаляйте используемые ID. `substitutes` задаёт кулинарные варианты, а не равнозначные замены по массе и КБЖУ: после замены пересчитываются порция, КБЖУ, вода, режим, время, `protein` и `freq`.

После изменения порций, рецептов или меню проверьте:

- разбор JSON, уникальность ID, все ссылки и значения перечислений;
- КБЖУ каждого приёма, правило `big`, ограничения по оборудованию;
- частоты и повторы на всём горизонте с учётом предыдущей истории;
- даты покупок, способ хранения и покрытие всех дней продуктами;
- суммы покупок, исключения, фрукты, остатки и число банок;
- актуальность `meta.counts`, `plan_sample.validation` и текста `status`.

Проверить только синтаксис JSON можно командой `python -m json.tool data.json > /dev/null` (Linux/macOS). Эта команда не проверяет логику меню. Отдельного файла JSON Schema в комплекте нет; `meta.schema_version` обозначает версию принятой структуры.
